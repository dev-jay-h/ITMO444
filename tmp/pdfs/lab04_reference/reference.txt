       2. Why This Matters                                                        
                                                                                  
       So far, “the uploader is down” has meant SSHing in or staring at a dead browser tab. Production teams don’t work
       that way — they define a Service Level Objective (SLO): a measurable target for how the system should behave
       (e.g., “95% of requests succeed,” “recovery from a failed instance takes under 3 minutes”), backed by a Service
       Level Indicator (SLI) — the actual metric you measure — and they build infrastructure that self-heals without a
       human racing to relaunch a server by hand.                                 
                                                                                  
       Today’s lab builds the smallest version of that pattern:                   
          An ALB is the single stable entry point — its DNS name doesn’t change even as the instances behind it come
          and go.                                                                 
          A Target Group continuously health-checks the instances registered to it, and stops sending traffic to ones
          that fail.                                                              
          An Auto Scaling Group notices when its instance count drops below the desired count (because you
          terminated one, or it failed a health check) and launches a replacement from the exact same Launch
          Template you already built — no manual run-instances required.          
          A Python script plays the role of an automated chaos/recovery test: kill something on purpose, measure how
          long the system takes to heal, and check that against your SLO — the same shape as a real incident
          postmortem’s “time to recovery” metric, just automated and repeatable.

       5. Part B — ALB Security Group and Tightening the App Security Group       
                                                                                  
       Read through this part to understand the two security groups involved; you’ll run the actual commands via the script
       in Part E, since they depend on resources ordering that’s easiest to get right in the script.
       The ALB security group is new, and is the only one that should be open to the whole internet — because the ALB is
       now the only intended entry point:                                         
                                                                                  
             aws ec2 create-security-group \                                      
              --group-name itmo-444-544-alb-sg \                                  
              --description "Allow inbound to the ALB on the app listener ports" \
              --vpc-id "$VPC_ID" \                                                
              --region us-east-2                                                  
             aws ec2 authorize-security-group-ingress --group-id <alb-sg-id> --protocol tcp --port 8080 --cidr 0.0.0.0/0
        region us-east-2                                                          
             aws ec2 authorize-security-group-ingress --group-id <alb-sg-id> --protocol tcp --port 8081 --cidr 0.0.0.0/0
        region us-east-2                                                          
       The app security group (itmo-444-544-app-sg, from the previous lab) currently allows port 3000 from 0.0.0.0/0.
       Now that the ALB fronts it, that’s more open than it needs to be — instances should only accept traffic from the ALB,
       not directly from the internet:                                            
                                                                                  
             aws ec2 revoke-security-group-ingress --group-id "$APP_SECURITY_GROUP_ID" \
              --protocol tcp --port 3000 --cidr 0.0.0.0/0 --region us-east-2      
             aws ec2 authorize-security-group-ingress --group-id "$APP_SECURITY_GROUP_ID" \
              --protocol tcp --port 3000 --source-group <alb-sg-id> --region us-east-2
                                                                                  
       --source-group instead of --cidr means “traffic is allowed only if it comes from something wearing this other
       security group” — not a specific IP range. This is why the ALB SG must exist before you can tighten the app SG: the
       rule directly references it.                                               
       ✅ Checkpoint: You can explain, in one sentence, why --source-group is a tighter rule than --cidr 0.0.0.0/0, even
       though both currently let traffic on port 3000 through.

       Also a read-through — Part E’s script runs the real, idempotent versions of these.

       A Target Group is what the ALB actually health-checks and routes to — not the instance directly:
                                                                                  
             aws elbv2 create-target-group \                                      
              --name itmo-444-544-uploader-tg \                                   
              --protocol HTTP --port 3000 \                                       
              --vpc-id "$VPC_ID" \                                                
              --target-type instance \                                            
              --health-check-protocol HTTP \                                      
              --health-check-path / \                                             
              --health-check-interval-seconds 10 \                                
              --health-check-timeout-seconds 5 \                                  
              --healthy-threshold-count 2 \                                       
              --unhealthy-threshold-count 2 \                                     
              --region us-east-2                                                  
        (cid:1) The defaults for a target group’s health check are a 30-second interval and a 5-check healthy/unhealthy
        threshold — safe for production, but that alone adds 2.5+ minutes to any recovery measurement before the
        ALB even notices. This lab tightens those to a 10-second interval and a 2-check threshold, so your SLO
        experiment isn’t dominated by health-check timing you didn’t choose on purpose. Real teams make this same
        trade-off deliberately: faster detection costs a few more health-check requests per minute (negligible), and buys
        meaningfully faster failover.                                             
       The Application Load Balancer itself spans both subnets:                   
                                                                                  
             aws elbv2 create-load-balancer \                                     
              --name itmo-444-544-app-alb \                                       
              --subnets "$SUBNET_A" "$SUBNET_B" \                                 
              --security-groups <alb-sg-id> \                                     
              --scheme internet-facing \                                          
              --type application \                                                
              --region us-east-2                                                  
       This takes a minute or two to become active — the script waits for it properly instead of guessing with sleep.
       Each Listener is a port on the ALB that forwards to one target group. Rather than path-based routing (which would
       mean changing the apps’ routes), this lab uses two ports on one ALB — simpler, and the apps don’t change at all:
                                                                                  
             aws elbv2 create-listener \                                          
              --load-balancer-arn <alb-arn> \                                     
              --protocol HTTP --port 8080 \                                       
              --default-actions Type=forward,TargetGroupArn=<uploader-tg-arn> \   
              --region us-east-2                                                  
       ✅ Checkpoint: You can explain, in one sentence, the difference between a target group and a listener.
                                                                                  
                                                                                  
       7. Part D — Auto Scaling Groups: The Recovery Mechanism                    
                                                                                  
                                                                                  
       An Auto Scaling Group’s job here isn’t scaling up — it’s maintaining a desired count. With min=max=desired=1, an
       ASG does exactly one thing: whenever the instance count drops below 1 (because you terminated it, or a health
       check failed it), it launches a replacement, from the Launch Template you already built, into one of the AZs you
       gave it.                                                                   
             aws autoscaling create-auto-scaling-group \                          
              --auto-scaling-group-name itmo-444-544-uploader-asg \               
              --launch-template "LaunchTemplateName=itmo-444-544-uploader-lt,Version=\$Latest" \
              --min-size 1 --max-size 1 --desired-capacity 1 \                    
              --vpc-zone-identifier "$SUBNET_A,$SUBNET_B" \                       
              --target-group-arns <uploader-tg-arn> \                             
              --health-check-type ELB \                                           
              --health-check-grace-period 120 \                                   
              --region us-east-2                                                  
                                                                                  
                                                                                  
                                                                                  

===== PAGE 5 =====
                                                                                  
                                                                                  
                                                                                  
                                                                                  
       Two flags matter more than they look:                                      
                                                                                  
          --health-check-type ELB — by default, an ASG only checks whether the EC2 instance itself is running (EC2
          status checks). ELB instead makes the ASG trust the target group’s health check — the same one that’s
          actually calling GET / on your app. An instance whose EC2 status is fine but whose Node process crashed would
          otherwise sit there marked “healthy” forever.                           
          --health-check-grace-period 120 — a fresh instance needs time to run dnf install, npm install, and start the
          service before it’s fair to judge it unhealthy. Without this, the ASG could decide a perfectly good but still-booting
          instance has failed and start churning it.                              
       Version='$Latest' is the same launch-template mechanic from the previous lab — any launch template version you
       publish (say, after editing app.js) is what the ASG uses for the next replacement, automatically.
       ✅ Checkpoint: You can explain, in one sentence, why --health-check-type ELB matters more here than it would for
       a single standalone instance.

             """Polls an HTTP endpoint and reports up/down transitions."""        
             import time                                                          
             import requests                                                      
                                                                                  
             def probe_once(url: str, timeout: float = 3.0) -> bool:              
               try:                                                               
                  resp = requests.get(url, timeout=timeout)                       
                  return resp.status_code == 200                                  
               except requests.RequestException:                                  
                  return False                                                    
             def wait_for_state(url: str, want_up: bool, poll_interval: float, max_wait: float, log_rows: list):
               """Poll `url` until it reaches the wanted state (up or down).      
                                                                                  
               Appends (elapsed_seconds, is_up) to log_rows on every poll. Returns the
               elapsed time in seconds when the target state was reached, or None if
               max_wait was exceeded.                                             
               """                                                                
               start = time.monotonic()                                           
               while True:                                                        
                  elapsed = time.monotonic() - start                              
                  if elapsed > max_wait:                                          
                    return None                                                   
                  is_up = probe_once(url)                                         
                  log_rows.append((round(elapsed, 2), is_up))                     
                  if is_up == want_up:                                            
                    return elapsed                                                
                  time.sleep(poll_interval)

             """Talks to the Auto Scaling Group this lab manages."""              
             import boto3                                                         
             def get_inservice_instance_id(asg_name: str, region: str):           
               client = boto3.client("autoscaling", region_name=region)           
               resp = client.describe_auto_scaling_groups(AutoScalingGroupNames=[asg_name])
               groups = resp.get("AutoScalingGroups", [])                         
               if not groups:                                                     
                  raise RuntimeError(f"Auto Scaling Group '{asg_name}' not found in {region}.")
               for inst in groups[0].get("Instances", []):                        
                  if inst.get("LifecycleState") == "InService":                   
                    return inst["InstanceId"]                                     
               return None                                                        
             def terminate_instance_via_asg(instance_id: str, region: str) -> None:
               client = boto3.client("autoscaling", region_name=region)           
               client.terminate_instance_in_auto_scaling_group(                   
                  InstanceId=instance_id,                                         
                  ShouldDecrementDesiredCapacity=False,                           
               )                                                                  
        (cid:1) terminate_instance_via_asg calls the Auto Scaling API, not ec2.terminate_instances.
         ShouldDecrementDesiredCapacity=False tells the ASG “this instance is going away, but desired capacity is still 1 —
        replace it.” Terminating the instance directly through EC2 would still eventually trigger a replacement once the
        ASG notices, but going through the ASG API is the deliberate, documented way to simulate this and makes the
        experiment’s starting point unambiguous.

               parser.add_argument("--poll-interval", type=float, default=2.0)

               if not probe_once(url):

               log_rows = []

       13. Key Terms Glossary                                                     
                                                                                  
          SLO (Service Level Objective) – A measurable target for how a system should behave, e.g. “recover within
          180 seconds.”                                                           
          SLI (Service Level Indicator) – The actual metric measured to check against an SLO — here, recovery time as
          measured by chaos_test.py.                                              
          TTR (Time to Recovery) – How long a system takes to return to a healthy state after a failure; the specific SLI
          this lab measures.                                                      
                                                                                  
                                                                                  
                                                                                  

===== PAGE 15 =====
                                                                                  
                                                                                  
                                                                                  
                                                                                  
          Application Load Balancer (ALB) – A Layer-7 load balancer that routes HTTP(S) traffic to target groups based
          on listeners and rules.                                                 
          Target Group – The set of instances (or other targets) an ALB health-checks and routes to; the ALB never
          routes to an instance directly.                                         
          Listener – A port + protocol on a load balancer that forwards matching traffic to a specific target group.
          Auto Scaling Group (ASG) – A resource that maintains a desired count of instances launched from a Launch
          Template, replacing any that disappear or fail health checks.           
          Health check grace period – The window after an instance launches during which an ASG won’t act on a
          failed health check, giving it time to finish booting.                  
          LCU (Load Balancer Capacity Unit) – The usage-based billing dimension for an ALB, on top of its hourly rate.
          Self-healing infrastructure – A system designed to automatically detect and recover from certain failures
          without manual intervention.
