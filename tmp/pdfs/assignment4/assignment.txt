          One paragraph explaining, using your own recovery-time numbers, what dominates the
          recovery window (health-check timing vs. boot/ npm install time vs. something else).
          In our chaos test, there was a total recovery window of about 45-60 seconds after the target
          instance was disrupted in 2.2 seconds—most of which was spent on **instance boot time and
          application initialization (e.g. running npm install and starting the Node.js service)** instead of
                                                                                    
          the health-check timing. Even though the 2 seconds probe interval (using --poll-interval) allowed
          us to split the down time and recovery process into very small parts, nearly all of the downtime
          was taken by AWS Auto Scaling setting up a new EC2 instance, executing user-data scripts,

          One paragraph explaining what changed in create_app_stack.sh / delete_app_
          stack.sh between the previous lab and this one — specifically, what replaced the old
          run-instances call and why.                                               
          In the current lab, **the previously discussed command `aws ec2 run-instances` for launching
          individual EC2 instances has now been totally replaced with the concept of AWS Auto Scaling
                                                                                    
          Groups (ASGs) combined with Application Load Balancer (ALB) and Target Groups**. The
          switch to this architecture serves the purpose of achieving high availability and automated
          redundancy; AWS is now able to monitor the health of the instances, spread the incoming load
          to multiple availability zones, and create replacement instances when one of the nodes fails
          during chaos testing instead of relying on the old static single-unit architecture.
